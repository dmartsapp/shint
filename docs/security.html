Reference

Security

Which releases get security fixes, how to report a vulnerability, how shint handles its dependencies' vulnerabilities, every release's software bill of materials - and every advisory so far, with its original sources.

Supported versions#

Security fixes go into the newest release only: use the latest release (shint --version says which one you have; the Docker tags latest, 4 and 4.2 follow it). Upgrading is the fix - see Install.

Older releases stay published, and are not patched. Their binaries, checksums, attestations and image tags are never deleted or replaced: anything pinned to one keeps working, every release can still be verified, and what a user ran can always be examined later. A release found to be affected by a vulnerability is listed in that vulnerability's advisory, with the release that fixes it. Taking a release down is kept for a release that is itself compromised - a tampered build, say - not for one that turns out to contain a known flaw.

Reporting a vulnerability#

Report it privately: Report a vulnerability, GitHub's private reporting on the repository's Security tab. Please do not open a public issue for a vulnerability that is not public yet.

Include what shint --version prints, the command you ran and what happened. The answer comes in the report itself, and the fix is credited to you unless you ask otherwise.

A vulnerability that is already public - in shint or in one of its dependencies - can go in an ordinary issue.

Dependencies#

shint is built with the Go toolchain and its standard library - which carries nearly all of its networking: DNS, TCP, UDP, HTTP and TLS - and a few modules: golang.org/x/net and golang.org/x/sys (from the Go project), github.com/spf13/cobra with its own dependencies, and github.com/dmartsapp/go-ping (maintained by this project). The dependency table lists their versions.

How their vulnerabilities are handled:

  • In the release cycle. When a dependency publishes a fix - a Go release, a new version of a module - shint moves to it in its next scheduled release (one every two weeks; see Branches and cadence).
  • Out of cycle, when it is serious. When a dependency's flaw is serious for shint as it is released - it changes what shint reports, or breaks how shint is used or the project's own tooling - shint gets a patch release outside the cycle, as soon as the fix is public. v4.2.4 was one.
  • Not liable for code we did not write. shint is provided "as is", without warranty of any kind, under its MIT license. The Go toolchain, its standard library and the modules shint uses are the work and the responsibility of their own authors. We follow their advisories and ship their fixes as described here, but we are not liable for flaws in code we did not write.

How releases are checked#

  • govulncheck, the Go project's vulnerability scanner, gates every release: the release workflows refuse to publish a release whose code reaches a known vulnerability in the Go vulnerability database. It also runs in every local make check (Testing).
  • It reports what shint's code can reach, not only what it contains: a vulnerability counts when there is a call path from shint to the vulnerable function. A path is not proof that the flaw can be triggered - it often needs conditions shint never creates - so each advisory below says how shint was affected in practice. shint takes the fix either way.
  • Between releases nothing scans on its own. By design, no workflow runs except for a release tag (the workflow trigger rule). An advisory published between two releases is found by the next make check or release - which is why the advisory below was found a month after its first fixes were published.
  • Every image is scanned too. From v4.3.0, Grype scans each Docker image's SBOM - shint's binary in it, and the distroless base's Debian packages, which govulncheck cannot see - and its report is kept on the release. Grype reports and does not gate: see Vulnerability reports.
  • Release integrity - checksums and signed build attestations for every binary - is described in Install; what each binary and image is made of, in its software bill of materials.

Software bill of materials#

Every release binary has a software bill of materials (SBOM) next to it on its release page, in both standard formats, JSON:

FileFormat
shint.linux.amd64.cdx.jsonCycloneDX 1.6
shint.linux.amd64.spdx.jsonSPDX 2.3

and so on for every binary - one pair each, because what is compiled in differs by platform: the Windows builds include github.com/inconshreveable/mousetrap, the others do not.

What an SBOM lists is what that binary was built from, read from the build information the Go toolchain embeds in every binary:

  • the binary itself: its SHA-256, the platform it is for, the commit it was built from, and the build settings (GOOS, GOARCH, CGO_ENABLED=0, -trimpath);
  • the Go standard library, as the Go release that built it: stdlib at go1.27.3 for this release, with the package URL pkg:golang/stdlib@... and the CPE cpe:2.3:a:golang:go:... that vulnerability scanners match the Go project's own advisories against - where every advisory so far has come from;
  • every Go module compiled in, with its version and its go.sum hash: golang.org/x/net, golang.org/x/sys, github.com/spf13/cobra, github.com/spf13/pflag and github.com/dmartsapp/go-ping.

shint's own license is given (MIT); the modules' licenses are left unasserted.

Use one with any tool that reads CycloneDX or SPDX - a vulnerability scanner such as Grype or OSV-Scanner, or Dependency-Track - to find out whether a release you run is affected by a vulnerability published after it:

Shell
curl -LO https://github.com/dmartsapp/shint/releases/download/v4.2.4/shint.linux.amd64.cdx.json
grype sbom:shint.linux.amd64.cdx.json

Verify one. From v4.3.0, each SBOM is made by the release workflow, in the job that builds its binary, and attested like the binary: a signed statement that this SBOM describes this exact file, made by the dmartsapp/shint workflow. With the GitHub CLI:

Shell
gh attestation verify shint.linux.amd64 --repo dmartsapp/shint --predicate-type https://cyclonedx.org/bom
gh attestation verify shint.linux.amd64 --repo dmartsapp/shint --predicate-type https://spdx.dev/Document/v2.3

The attestation carries the SBOM itself (--format json prints it), so it is also proof that the file next to the binary is the one the workflow made.

Releases before v4.3.0 - v4.0.0 to v4.2.4 - got their SBOMs on 2026-11-09, made from their published binaries by the same script, after each binary was checked against the SHA-256 that GitHub records for it. They say so (the CycloneDX lifecycle is post-build; the SPDX package comment says it) and they are not attested: an attestation is made by the workflow at the build, and those builds are long finished. The binary's SHA-256 in each SBOM ties it to its file. The v4.0.x releases have no checksum files, and v4.0.0 to v4.0.6 no attestations either; their SBOMs still name the Go release that built them.

How they are made. .github/scripts/sbom.py reads the build information with go version -m -json - which reads the binary and never runs it - and writes both formats; no third-party tool makes the binaries' SBOMs. (Go's reader finds nothing in AIX's XCOFF binaries; for those the script reads the same block from the file itself, the way the toolchain does.)

Docker images#

From v4.3.0, the Docker images - Docker Hub and GHCR, linux/amd64 and linux/arm64 - have SBOMs too, in both formats, one pair per registry and platform, on the release page:

FileWhat
image.ghcr.linux.amd64.cdx.json, .spdx.jsonthe GHCR image for linux/amd64
image.ghcr.linux.arm64.cdx.json, .spdx.jsonthe GHCR image for linux/arm64
image.dockerhub.linux.amd64.cdx.json, .spdx.jsonthe Docker Hub image for linux/amd64
image.dockerhub.linux.arm64.cdx.json, .spdx.jsonthe Docker Hub image for linux/arm64

An image holds more than shint's binary: the distroless base's Debian packages - CA certificates, time zones, the user and group files - so its SBOM lists those as well, and the image's own shint binary (built in the Dockerfile, not the one on the release page) with its Go release and modules. Syft makes them, in the image workflows, from the pushed image by each platform's digest; it is pinned, and its download checked against a SHA-256 pinned in the repository, before it runs.

Each is attested against its platform's image digest. GHCR's attestations are also pushed to the registry, beside the image, for registry-aware tools; Docker Hub's are kept on GitHub. Either way:

Shell
docker buildx imagetools inspect ghcr.io/dmartsapp/shint:v4.2.4      # each platform's digest
gh attestation verify oci://ghcr.io/dmartsapp/shint@sha256:<digest> --repo dmartsapp/shint --predicate-type https://cyclonedx.org/bom

(https://spdx.dev/Document/v2.3 for the SPDX one; docker.io/<user>/shint for Docker Hub's.) Images before v4.3.0 have none.

Vulnerability reports#

From v4.3.0 every release keeps its scans' reports beside its files, for as long as it exists:

  • govulncheck.txt - the report of the check that gated the release: the modules and the Go release scanned, and what was found. It used to live only in the workflow run's summary, which GitHub deletes after its retention period.
  • image.<registry>.linux.<arch>.grype.json - Grype's scan of each image's SBOM: every match of a package and version - the Go standard library, the modules, the base image's Debian packages - against vulnerability databases, with its severity. Read one with:
Shell
jq -r '.matches[] | [.vulnerability.severity, .vulnerability.id, .artifact.name, .artifact.version] | @tsv' image.ghcr.linux.amd64.grype.json

Grype reports; it does not decide. It matches versions with no reachability analysis, so it also lists flaws in code shint never calls, and a Debian package's flaw that does not matter in a distroless image. govulncheck, which follows call paths from shint's own code, stays the gate. A Grype match that does matter is handled like any other advisory: in the release cycle, or out of it when it is serious.

Advisories#

2026-11-08: Go 1.27.1 standard library#

Affectedshint v4.0.0 to v4.2.3: every binary and container image, all built with Go 1.27.1 and golang.org/x/net v0.59.0. Older lines (v3 and before) were built with older Go releases and are not supported.
Fixed inv4.2.4, released 2026-11-08: built with Go 1.27.3 and golang.org/x/net v0.62.0
What to doUpgrade to v4.2.4 or later (Install). A Docker image pulled by latest, 4 or 4.2 gets it on the next pull. Building an older version from source with a current Go also gets the fixed standard library (its x/net stays at v0.59.0, whose advisories shint does not reach).
Issue#91

What happened. The Go project published fixes for ten vulnerabilities in its standard library that shint's code reaches - nine in Go 1.27.2 (October 8, 2026) and one in Go 1.27.3 (October 21) - after shint v4.2.3 (September 26) was built with Go 1.27.1. govulncheck found them on November 8, in a local make check during the v4.3.0 work, and v4.2.4 shipped the same day as an out-of-cycle security patch.

The last two are in golang.org/x/net/html, which shint does not import - govulncheck reported them as present but not reached - and are listed because v4.2.4 moved past them too.

How shint was affected. One of them changed what shint could report, and one needs a request only a user can ask for; the rest were reachable in the code, but need conditions shint does not create:

AdvisoryHow shint was affected
GO-2026-6809Affected. web verifies every HTTPS certificate with crypto/x509. Where the trust store had not been updated to drop these intermediates - a container image's CA bundle is fixed when the image is built - web could accept a certificate chained through one, and report a response instead of a certificate error.
GO-2026-6605Only with web -X CONNECT and a body. web uses no proxy, so it never sends a CONNECT of its own; asked for one with --data, and refused with a keep-alive answer, a later attempt of the same run (--count) could read the wrong response.
GO-2026-6613Not in practice - tested with v4.2.3 and v4.2.4. A real CONNECT host:port is answered 404 by listen http, never a 2xx; even an unusual CONNECT /, answered 200, has its connection closed after the answer, and a request sent behind it is never served.
GO-2026-6610Not in practice. The flaw is in the HTTP/2 transport acting as a reverse proxy; web speaks HTTP/1.1 only, and forwards nothing.
GO-2026-6611Not in practice. It needs an HTTP/2 connection; web speaks HTTP/1.1 only, and listen http serves HTTP/1.1 only.
GO-2026-6617Not in practice. HTTP/2 servers only; listen http serves plain HTTP/1.1 and never enables HTTP/2.
GO-2026-6612Not in practice. HTTP/2 servers only, as above.
GO-2026-6603Not in practice. HTTP/2 servers only, as above.
GO-2026-6607Not in practice. A flaw of TLS servers; shint runs none (web is a TLS client, listen http has no TLS).
GO-2026-6608Not in practice. Multipart form parsing; shint parses no multipart forms (listen http reads request bodies without parsing them).
GO-2026-6866Not affected. In golang.org/x/net/html, which shint does not import. Cleared anyway by moving to x/net v0.62.0.
GO-2026-6860Not affected. As above.

What was done, in v4.2.4 (dac550f):

  • go.mod names Go 1.27.3 - the version every workflow builds the binaries with - and golang.org/x/net v0.62.0 (v0.60.0 would have been enough for the reachable ones; v0.62.0 also clears the two in x/net/html). govulncheck finds no vulnerabilities at all.
  • The container images are built with golang:1.27.3-alpine, and a test now fails if the Dockerfile and go.mod ever name different Go releases, so the images and the binaries cannot drift apart.
  • golangci-lint moved from v2.13.2 to v2.15.0: Go 1.27.3 writes compiled packages in a newer format that v2.13.2 cannot read.
  • How to move to a new Go release, for the next one, is written down: Moving to a new Go release.
